# Связь архитектуры с интерфейсами

Архитектуры тесно связана с интерфейсами. Например, добавление плагина должно быть допустимо архитектурой и для этого определяется необходимый интерфейс. Несмотря на то, что внутри некого модуля может быть написано все, что угодна именно его API определяет его функционал.

# Общая архитектура

Для взаимосвязи между модулями выбрана архитектура COM, позволяющая исключить большинство зависимостей между модулями, возложив их на интерфейсы. Также большим плюсом COM является возможность контроля версий интерфейсов и обеспечения обратной совместимости. 

У приложения есть 2 типа плагинов - сервисы, указатели на которых хранятся в `App` и обычные плагины, подключаемые в менеджере плагинов.  

Исключения запрещены. 
Для обработки ошибок используется сервис логгера

# Архитектура приложения

У приложения есть одно ядро (скорее всего `singleton`), где хранятся указатели на базовые сервисы, без которых приложение в принципе запускаться не может.
Основной цикл пока работает в `class Object` (см. дальше).


## Обработка событий от пользователя и отображение экрана

Событие от пользователя - это `struct Event`. В нем предполагается хранить текущий тип события(`mouseEvent`, `keyEvent`) и информацию для него.
Реализация либо через `union`, либо через `std::variant`.

Для получения Event есть отдельный интерфейс `class InputController`, который определяет методы ` bool pullEvent()`, благодаря которым получается текущий ивент.

Для обработки событий и отрисовки используется N-мерное дерево объектов. Объект - это полностью виртуальный `class AObject`, который объединяет в себе графическую и логическую составляющие.

Менеджер объектов (по факту корень дерева) доступен по указателю из App.

### Как происходит обработка событий

У каждого объекта есть метод `run` - запускающий основной цикл. 
Цикл состоит из следующий этапов:
- Получение события от пользователя (либо в очередь, либо сразу обработка)
- Обработка события методом `bool processEvent(Event)`. Если функция возвращает `true` - то значит событие поглощено этим объектом (или его детьми) и родитель, которому пришло `true` - также возвращает `true`.
- Рендер всех объектов через `App`.

Важно: `run` - перехватывает поток выполнения. Из него будет вызываться все `render`, `eventProcess` и т.д.. 

В обработке событий `Event` сначала посылается последнему ребенку, если он его не поглотил - предпоследнему и т.д.
В рендере наоборот - отрисовка идет с первого к последнему.

Если окну необходимо стать модальным - то оно запускает внутри себя главный цикл и таким образом перехватывает управление до какого-то ему необходимого события.

Встает вопрос - как хранятся положение объекта и его размеры: 
- для настройки визуала UI удобнее использовать координаты относительно родителя(либо в виде 50 пикселей от начала родителя, либо 0.1 * parentWidth относительно начала родителя) и относительные размеры(не факт)
- для рендера и обработки нажатия мыши лучше подходят глобальные координаты
- для переноса окна и добавления объектов в окно почти необходимы координаты относительно начала родителя.

(!!!) Возможно положение - в большей степени детали реализации этого менеджера, но не факт.

Пока возникают следующие проблемы:
- Модальное окно нужно рендерить последним, но свое положение внутри дерева оно не меняет.
- Каким образом хранятся размеры и положение объекта.
- Как будет храниться информация о действии, которое нужно сделать(одна или вектор `std::function`(где будут в основном лежать лямбды с захватом необходимых значений) | одна или несколько команд с функцией `execute`). При использовании паттерна команда она сразу будет исполняться или будет передана в очередь команд.
- Если необходимо удалить окно, то удаление произойдет сразу-же или просто выставиться флаг о необходимости удаления. (в большей степени относиться к предыдущему вопросу)


### Работа с плагинами

Для удобного взаимодействия с плагинами нужен интерфейс добавления новых объектов в дерево.
Очевидно, должны быть какие-то способы идентификации объектов в дереве. 

Пока есть 2 варианта:
- Просто ID. Если ID нет(например плагин добавляет окно настроек) - то новый объект подвязывается к корню. Если нужно что то добавить к новому объекты - храните его ID.
- ID + какой-то более общий идентификатор. Можно использовать `std::string`. Например плагин добавляет новое окно. У этого окна будет имя: `<PluginName>:SettingWindow`. Если нужно будет добавить к нему что-то - можно будет просто прописать имя. У этого способа возникает проблемы дублирования поиска и возможные коллизии между именами (вроде как должны фикситься именем плагина).

Также хочется отказаться от необходимости написания окон и кнопочек для каждого плагина.
Есть предложение создания `UI Framework`, в котором будут стандартизированные окна и кнопки с различными настройками. 
Этот фрейворк сам будет заниматься базовыми текстурами для кнопок и окон, их расположением внутри окна, добавлением других объектов.

Примеры желаемого взаимодействия:
- Базовая кнопка. Пользователь дает переднюю картинку и список функций/команд исполнения. Фреймворк сам выберет цвета для объекта, настроит обработку действий.
- PoolMenu. Пользователь создает меню и добавляет в него объекты(скорее всего API только для кнопок). Меню само распределит им место, возможно изменит свой размер.

При использовании такого фреймворка не нужно париться насчет собственных текстур и общего вида приложения.
